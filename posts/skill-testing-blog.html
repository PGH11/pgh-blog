Skill 测试实战：从脚本到 Agent 的分层验收方法

这篇文章记录在「视频创作 Agent」项目中，怎么把 Skill（脚本 + API 封装）和 Agent（LangGraph 图编排）拆开测试，最终合到一起验收。核心思路：底座先绿，再上编排。

---

一、为什么要分层测 Skill

Skill 是能力层：真正发起 HTTP、处理 multipart、解析返回、落盘下载的都在这里。Agent 是调度层：它决定读哪份 SKILL.md、调哪个脚本、参数怎么拼。

如果一上来只让 Agent 发起「帮我做个视频」，一旦失败，你根本分不清是：

  • 意图没识别对；
  • 环境变量里的 access key 没配好；
  • API 返回字段变了，脚本解析挂了；
  • 网络或鉴权 401；
  • 还是下载 URL 本身需要特殊 header。
先把脚本在终端里跑通，等于把问题先压缩到「API + 解析 + 文件 IO」这一层；再上 Agent，这时只剩「识别与编排」两类问题，排障会快一个数量级。

类比：先确认发动机和油管没问题，再让「自动驾驶」上路；否则出了事故你都不知道是车坏了还是导航错了。

三、四层测试模型

第 1 层：静态与参数层（几乎零成本）

  • python -m py_compile 把所有脚本过一遍，消灭语法和 import 级错误。
  • 每个入口 --help 看一遍，确认必填参数和文档一致。
  • 检查 settings.py 里的默认值是否合理（如 MEMORY_FILE、KNOWLEDGE_DIR 路径是否存在）。

这一层的目标是：别让低级错误混进集成测试。

第 2 层：负向与边界层（不依赖真实创作成功）

  • 不配 ARK_API_KEY 时是否明确提示「请设置环境变量」。
  • 不配 LitMedia token 时 submit_text_to_video 是否报错而不是静默失败。
  • 缺必填参数（如 prompt 为空）是否在 route_after_reflection 被拦截。
  • 上传不存在的图片 URL 时图生路径是否正确降级。
  • memory_store.py 的 user_memory.json 不存在或格式损坏时是否能自动修复/重建。

好的失败信息能省掉大量「用户在群里问为什么没反应」的时间。

第 3 层：平台 API 与闭环层（真链路的验收）

按能力拆开测：

  • submit_text_to_video：能否返回有效的 task_id，接口是否 200。
  • submit_image_to_video：给合法图片 URL 时能否正常提交，缺图 URL 时是否失败。
  • memory_store：读写 user_memory.json 是否正常，旧版格式能否自动迁移（migrate_legacy_memory）。
  • rag_service：knowledge/*.md 存在时能否检索到相关片段，不存在时是否返回空列表而不是报错。
很关键的一点：rag_service 的检索逻辑可以用本地 Markdown 文件测，不必依赖外部服务。这样「检索逻辑」和「外部 API」解耦。

再手工跑一遍完整闭环：提交 → （可能轮询状态）→ 确认接口返回。若这一步不靠 Agent 也能走通，说明底座是稳的。

第 4 层：Agent 与 Skill 层（意图识别 ≠ 有回复）

很多人把「Agent 回话了」当成测试通过。更硬的标准是一条链：

> 自然语言 → 是否命中 skill → 是否选对工作流 → 是否调对工具 → 参数是否对齐 → 用户是否看到结果。

举例：

  • 「生成一张小猫图片」→ 应调 submit_text_to_video，且 prompt 应保持用户意图，不要 AI 擅自加「电影级、8K、超写实」这类词——若 CREATIVE_PROMPT 里写了「只做传话」，这就是回归项。
  • 「用这张图 https://xxx.png 做个视频」→ 应走 i2v 路径，先 asset_resolver 解析 URL，再调 submit_image_to_video，且 img_url 应对上。
  • 「确认生成」但还没 awaiting_confirmation → 不应走到 tool_executor，应被 reflection_worker 拦截。
SKILL.md 不是玄学 prompt 工程，而是产品规格书：description 决定「什么时候该被选中」，正文里的原则决定「选中以后该怎么干」。测试时要专门设一批触发句式 + 必须执行的动作，做成小矩阵，比单靠感觉聊天靠谱得多。

四、当前项目的特殊测试点

4.1 文生 vs 图生工具的区分

当前代码有两个工具：submit_text_to_video 和 submit_image_to_video。

测试时需要确认：

  • 文生路径不会误调 submit_image_to_video。
  • 图生路径不会误调 submit_text_to_video（i2v_worker 里会纠正这种错误）。
  • route_after_reflection 的判定逻辑：图生需要同时满足 prompt 非空和 source_image_url 非空。

4.2 结构化输出空返回

模型偶发返回 None。当前代码用 invoke_structured_with_recovery 三层治理：

  • 主路径正常返回。
  • 第一次为空：追加 HumanMessage 重试。
  • 仍为空：降级为澄清回复。

测试时可以人为触发空返回（比如临时把模型返回 mock 为 None），验证：

  • 图不会崩掉。
  • 用户看到的是一条合理的追问，不是报错。
  • DEBUG 日志里有 structured_output_observation 记录。

4.3 长期记忆的读写

memory_store.py 的几个边界：
  • 文件不存在时自动创建空结构。
  • 旧版 5 个数组格式能自动迁移到 memories 条目结构。
  • confirmed_prompt 类别只保留最近 5 条。
  • memory_id_for 生成稳定 id，同一条记忆不会重复写入。

4.4 RAG 检索

rag_service.py 的几个边界：
  • knowledge/ 目录不存在时返回空列表。
  • 中文分词：tokenize_for_rag 会按 2 字粒度切中文，并有同义词扩展。
  • split_markdown_sections：过长片段会按 RAG_CHUNK_MAX_CHARS 再切。

五、容易被忽略的坑

上传返回值字段名

文档里可能叫 asset_id，代码里若取的是平台返回的另一个字段，一联调就会「上传成功但下游不认」。这类问题必须在「上传 + 带 asset 提交」这一条用例里显式验掉。

结构化输出 method 不匹配

langchain_openai 版本不同，with_structured_output() 的默认 method 可能从 function_calling 变成 json_schema。如果底层模型不支持 json_schema，就会 400。当前代码显式写 method="function_calling"，测试时要确认这一点没被改掉。

图生路径缺图

图生路径有三层保护：i2v_worker 压 tool → reflection_worker 硬拦截 → route_after_reflection 三重检查。测试时要专门验证缺图场景不会误提交。

记忆噪声

memory_writer 如果没有门槛，会把所有一次性对话都写进长期记忆。当前代码里是模型判断 + Python 置信度门槛。测试时要验证"你叫什么名字"这类闲聊不会写进记忆。

FrontendParams 新增字段

当前 FrontendParams 比 CreativeParams 多了 open_filter、sound_effect_switch、seed、is_feed 等字段。这些字段在工具调用时需要合并到 payload 里。测试时要确认这些字段没有被漏掉。

六、推荐执行顺序（checklist）

  • 全脚本 py_compile + import 验证。
  • 不配 key、缺参数、坏 URL 等负向用例。
  • memory_store.py：空文件/损坏文件/旧版格式的读写。
  • rag_service.py：无 knowledge 目录/有目录的关键词检索。
  • litmedia_client.py：最小文生 + 图生冒烟。
  • 手工闭环：提交 → 检查接口返回。
  • 图路径层：覆盖 chat / creative / i2v 三条主要分支。
  • 结构化输出：验证重试和降级。
  • 记忆写入：验证写入门槛和裁剪逻辑。
  • 最后才是 Agent：用固定话术矩阵测触发与工作流。

---

七、小结

Skill 测试的本质是分层验收：脚本保证「机器和 API 说得通」，Agent 测试保证「人和意图被正确翻译成那几行命令」。两层都绿，再说「Skill 已生产就绪」才站得住脚。

若要把这套东西产品化，可以把「意图矩阵」和「手工命令 checklist」放进仓库，每次发版前 CI 跑静态层，发版后人工或半自动跑一层 API 冒烟——这比赌一次「让模型随便聊聊」要可靠得多。
