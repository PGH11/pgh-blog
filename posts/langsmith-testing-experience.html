LangSmith 测试经验

这份文档记录当前视频创作 Agent 接入 LangSmith 后，怎么观察、怎么排查、怎么判断一次对话是不是正常。实现代码在 video_agent 包内；根目录 image_agent.py 仅为兼容入口（转发到 video_agent.cli）。

1. 先看项目是否接对

当前脚本里硬编码了：

LANGSMITH_PROJECT_VALUE = "test"

所以 trace 应该出现在 LangSmith 的：

Tracing -> test

如果看不到数据，先检查这几件事：

  • 运行的是当前项目（python -m video_agent 或 python image_agent.py）。
  • LANGSMITH_API_KEY_VALUE 已经填了真实 key。
  • configure_langsmith() 在模型初始化之前执行。
  • 页面左侧选的是 Tracing，不是 Monitoring。
  • 项目名是 test，不是之前的 litmedia-video-agent。

LangSmith 有时会有几秒延迟，运行完一轮对话后可以刷新一下页面。

2. 一条 trace 对应什么

现在代码里每次执行：

state = app.invoke(
    state,
    config={
        "run_name": "video_creation_agent",
        "tags": ["cli", "langgraph", "litmedia"],
        "metadata": {
            "route": state.get("route"),
            "awaiting_confirmation": state.get("awaiting_confirmation"),
            "has_prompt": bool(state["params"].prompt),
            "has_long_term_memory": bool(state.get("long_term_memory")),
            "should_retrieve": state.get("should_retrieve"),
            "retrieval_query": state.get("retrieval_query"),
            "rag_sources": state.get("rag_sources", []),
            "has_source_image": bool(state["params"].source_image_url),
        },
    },
)

所以 LangSmith 里一条 video_creation_agent 基本对应一次用户输入。

比如用户连续输入三次：

我想做一个小狗视频
第一个不错
确认生成

通常就会看到三条 video_creation_agent run。

3. 左侧树结构怎么看

点开一条 trace，左侧会出现类似结构：

video_creation_agent
  ├─ memory_retriever
  ├─ retrieval_router
  │   └─ ChatOpenAI
  ├─ route_after_retrieval（条件边，不调模型）
  ├─ rag_retriever（可选，仅当 should_retrieve=True）
  ├─ intent_router
  │   ├─ Python 快捷路径（i2v，不调模型）
  │   └─ ChatOpenAI
  ├─ route_by_intent（条件边，不调模型）
  ├─ chat_responder / creative_worker / asset_resolver → i2v_worker
  │   └─ ChatOpenAI（结构化节点可能显示 RunnableSequence）
  ├─ reflection_worker（creative/i2v 路径）
  │   └─ ChatOpenAI
  ├─ route_after_reflection（条件边，不调模型）
  ├─ tool_executor（可选，仅当工具调用被放行）
  └─ memory_writer
      └─ ChatOpenAI

不一定每次都有所有节点。

常见情况：

  • 闲聊：memory_retriever → retrieval_router → intent_router → chat_responder → memory_writer。
  • 文生创作：... → intent_router → creative_worker → reflection_worker → route_after_reflection → memory_writer。
  • 图生创作：... → intent_router → asset_resolver → i2v_worker → reflection_worker → ...。
  • 确认生成：如果工具调用没被反思节点拦截，会出现 tool_executor，之后仍会进入 memory_writer。

4. 每个节点重点看什么

4.1 video_creation_agent

这是整轮对话的总入口。

先看这里可以快速知道：

  • 用户这一轮输入是什么。
  • 最终输出给用户的回复是什么。
  • 这轮有没有报错。
  • 总耗时是多少。

如果只想快速判断这轮是否正常，先看最外层就够。

4.2 memory_retriever / retrieval_router / rag_retriever / memory_writer

这四个节点是记忆与检索链路：

  • memory_retriever：读取本地 user_memory.json，把长期记忆注入本轮上下文。
  • retrieval_router：AI 判断本轮是否需要 RAG，并给出 retrieval_query；同时清空上轮的 rag_context。
  • rag_retriever：仅在需要时出现；走本地 Markdown 关键词匹配检索。
  • memory_writer：每轮收尾，AI 决定是否写入长期记忆，再由 Python 合并、裁剪、落盘。

排查建议：

  • 发现"明明该检索却没检索"，先看 retrieval_router → Output。
  • 发现"检索结果不相关"，看 retrieval_query 是否合理，以及 rag_retriever 的 sources 和 scores。
  • 发现"记忆没更新"，看 memory_writer → Output 的 should_write 和 accepted_memories。

4.3 intent_router

这个节点负责判断路由：

chat / creative / i2v

注意：i2v（图生视频）有Python 快捷路径——当用户输入包含图片 URL 且命中「图生」类关键词时，直接设 route="i2v"，不调路由模型。

重点看 Output 里的：

{
  "route": "creative",
  "reason": "..."
}

排查方式：

  • 用户问"你能帮我干嘛"，应该是 chat。
  • 用户说"我想做一个小狗视频"，应该是 creative。
  • 用户说"用这张图做个视频"且含图片 URL，应该是 i2v（走快捷路径）。
  • 用户说"确认生成"，如果正在等待确认，应该是 creative。

如果路由错了，优先改 ROUTER_PROMPT，不要急着改后面的节点。

4.4 route_by_intent / route_after_retrieval / route_after_reflection

这三个都是条件边函数，不调用模型，只读 state 字段做映射：

  • route_by_intent：读 state["route"]，映射到 chat_responder / creative_worker / asset_resolver。
  • route_after_retrieval：读 should_retrieve 和 retrieval_query，决定走 rag_retriever 还是 intent_router。
  • route_after_reflection：读 tool_call.tool_name + params.prompt + params.source_image_url，决定走 tool_executor 还是 memory_writer。

它们耗时通常接近 0。如果出问题，一般是上游节点写入的字段不对。

4.5 chat_responder

这个节点处理闲聊、能力介绍、上下文问答。

重点看：

  • Input 里的 chat_history 是否带上了最近对话。
  • Input 里的 params 是否包含当前 prompt。
  • Input 里的 long_term_memory 和 rag_context 是否有值。
  • Output 里的 reply 是否回答了用户的问题。

典型测试：

你能帮我干嘛？
我刚刚说了什么？
现在的 prompt 是什么？

4.6 creative_worker

这是文生视频的核心创作节点。

重点看 Output：

{
  "intent": "create_prompt",
  "generation_mode": "text_to_video",
  "params_patch": {
    "prompt": "...",
    "negative_prompt": "..."
  },
  "merge_strategy": "fill_missing",
  "reply": "...",
  "ready_for_submit": true,
  "confirm_submit": false,
  "tool_call": {
    "tool_name": "none"
  }
}

检查点：

  • 用户只说"小狗视频"时，不应直接提交，应给创意方向。
  • 用户选择"第一个"时，应整理出完整 prompt。
  • 用户说"改成更搞笑"，应覆盖旧 prompt。
  • 用户确认生成时，才应出现 tool_call.tool_name = submit_text_to_video。

如果结构化输出为空，节点会走 invoke_structured_with_recovery 重试一次；仍为空则用 generate_clarification_reply 生成澄清回复。在 LangSmith 里可以观察到 structured_output_observation 的日志。

4.7 asset_resolver / i2v_worker

图生视频路径上的两个节点：

  • asset_resolver：从用户输入、params、resolved_image_url 中解析图片 URL，写回 source_image_url / resolved_image_url。
  • i2v_worker：图生专用结构化节点（独立 prompt I2V_PROMPT），产出与 creative_worker 类似的状态字段。

重点关注：

  • params.source_image_url 是否被正确解析。
  • 缺图时，tool_call 是否被压掉（tool_name="none"）。
  • 如果 AI 误返回 submit_text_to_video，节点内会自动纠正为 submit_image_to_video。

4.8 reflection_worker

这个节点是安全检查层。

它负责判断：

  • prompt 是否太泛。
  • 用户是否真的确认提交。
  • reply 有没有提前说"已经生成成功"。
  • tool_call 是否应该被阻止。
  • 图生路径是否缺 source_image_url。

重点看 Output：

{
  "passed": true,
  "should_block_tool": false,
  "issues": [],
  "revised_reply": null
}

如果它阻止了工具调用，通常会看到：

{
  "should_block_tool": true,
  "issues": ["用户尚未明确确认生成"]
}

图生路径缺图时，reflection_worker 会额外做一次硬拦截，即使模型没拦。

4.9 tool_executor

只有 Agent 决定调用工具，且反思节点没有阻止时，才会进入这里。

当前支持两种工具：

  • submit_text_to_video：文生视频。
  • submit_image_to_video：图生视频。

重点看：

  • tool_name 是否正确。
  • tool 入参里的 prompt、img_url（图生）是否正确。
  • 前端 UI 参数是否合并正确（含 open_filter、sound_effect_switch、seed、is_feed）。
  • 接口返回是否成功。

如果没看到 tool_executor，说明还没真正提交。

排查顺序：

creative_worker / i2v_worker 是否返回 tool_call？
reflection_worker 是否拦截？
route_after_reflection 是否走 tool？

5. Input / Output 怎么看

每个节点右侧都有 Input 和 Output。

Input

Input 是节点执行前拿到的状态。

常见字段：

user_input
params（含 prompt / negative_prompt / source_image_url）
frontend_params
chat_history
long_term_memory
rag_context / rag_sources
resolved_image_url
awaiting_confirmation
tool_call
reflection_passed / reflection_issues

看 Input 是为了确认：

  • 上一轮状态有没有保存下来。
  • 当前 prompt 是否已经存在。
  • 当前是不是等待确认状态。
  • 长期记忆和 RAG 上下文是否注入。
  • 图生路径的图片 URL 是否解析。

Output

Output 是节点执行后返回的新状态。

看 Output 是为了确认：

  • 这一步有没有更新 prompt / source_image_url。
  • 有没有生成 reply。
  • 有没有设置 awaiting_confirmation。
  • 有没有设置 tool_call。
  • 有没有进入 is_ready。
  • 记忆是否写入。

6. 什么时候看 ChatOpenAI 子节点

如果只看业务流程，通常看父节点 Output 就够。

需要深入排查模型输入输出时，再点 ChatOpenAI：

  • Input：真实发给模型的 messages。
  • Output：模型原始响应。

尤其是排查这些问题时要看 ChatOpenAI：

  • AI 为什么判断成 chat / creative / i2v。
  • AI 为什么没有提取 prompt。
  • AI 为什么没有设置 tool_call。
  • AI 为什么误以为已经确认。
  • 结构化输出是否返回了 null（触发重试/降级）。

注意：使用 with_structured_output(..., method="function_calling") 的节点在 LangSmith 里可能会显示：

RunnableSequence
  └─ ChatOpenAI

这是正常的。当前脚本所有结构化节点都显式指定了 method="function_calling"，所以在 ChatOpenAI 的请求里不应该看到 response_format.type=json_schema。如果看到它，说明某个 with_structured_output(...) 还没有补上 method 参数，或者运行的不是当前代码。

7. 常见问题排查

7.1 看不到 trace

检查：

  • 项目名是不是 test。
  • LANGSMITH_API_KEY_VALUE 有没有填真实 key。
  • 是否重新启动了脚本。
  • 是否在 Tracing 页面，而不是 Monitoring 页面。

7.2 route 错了

看：

intent_router → Output

注意区分：走的是 Python 快捷路径还是模型判断。图生路由走快捷路径时不调模型，LangSmith 里不会出现 ChatOpenAI 子节点。

如果 route 错，改：

ROUTER_PROMPT

或者调整 intent_router() 里的快捷路径关键词列表。

7.3 prompt 没更新

看：

creative_worker / i2v_worker → Output → params

如果 params.prompt 没变，再看：

creative_worker / i2v_worker → ChatOpenAI → Output

判断是模型没返回，还是合并逻辑没覆盖。

7.4 工具没调用

按顺序看：

creative_worker / i2v_worker → tool_call
reflection_worker → should_block_tool
route_after_reflection
tool_executor 是否出现

常见原因：

  • 用户没有明确确认。
  • prompt 太泛，被反思节点拦截。
  • 图生路径缺 source_image_url，被 i2v_worker 或 reflection_worker 拦截。
  • tool_call.tool_name 是 none。

7.5 工具调用了但接口失败

看：

tool_executor → Output

以及 DEBUG 日志里的 LitMedia payload。

重点检查：

  • token 是否有效。
  • signature 是否生成。
  • prompt 是否为空。
  • 图生路径的 img_url 是否可访问。
  • UI 参数是否合理（含 open_filter、sound_effect_switch）。
  • 接口返回的错误 body。

7.6 json_schema is not supported by this model

这类报错通常长这样：

InvalidParameter: response_format.type=json_schema is not supported by this model

排查顺序：

  • 先看报错发生在哪个节点。
  • 再看这个节点是否用了 with_structured_output(...)。
  • 检查代码里是否显式写了 method="function_calling"。

原因是 with_structured_output() 在 langchain_openai >= 0.2 默认使用 method="json_schema"，但 Ark 等兼容接口不一定支持。当前代码写法：

router_llm = llm.with_structured_output(RouteDecision, method="function_calling")
creative_llm = llm.with_structured_output(CreativeUnderstanding, method="function_calling")
reflection_llm = llm.with_structured_output(ReflectionResult, method="function_calling")
memory_llm = llm.with_structured_output(MemoryWriteDecision, method="function_calling")
retrieval_llm = llm.with_structured_output(RetrievalDecision, method="function_calling")

经验：不要依赖默认 method，显式写 function_calling 把行为固定下来。 不同环境安装的 langchain-openai 版本可能不同，默认值可能从 function_calling 变成 json_schema，导致"公司能用家里不能用"的问题。

7.7 结构化输出返回 None

模型偶发返回空结构化结果。当前代码用 invoke_structured_with_recovery 处理：

  • 主路径：正常结构化调用。
  • 第一次拿到 None：追加一条「必须返回合法 schema」的 HumanMessage，重试一次。
  • 仍为 None：用 generate_clarification_reply 调普通 llm 生成澄清回复。
  • 观测：在 DEBUG 或 LangSmith 里可看到 structured_output_observation 日志，区分「首空」「重试恢复」「二次仍空」。

7.8 Windows 控制台 UnicodeEncodeError

如果普通聊天已经走通，但打印回复时报：

UnicodeEncodeError: 'gbk' codec can't encode character

一般是模型回复里包含 emoji 或特殊符号，而 Windows 终端当前编码是 GBK。

当前脚本用这个配置兜底：

if hasattr(sys.stdout, "reconfigure"):
    sys.stdout.reconfigure(encoding="utf-8", errors="replace")

这属于 CLI 输出问题，不是 LangGraph、LangSmith 或模型调用逻辑问题。

7.9 图生路径缺图

图生路径有多层保护：

  • i2v_worker：缺图时压掉 tool_call，设 tool_name="none"。
  • reflection_worker：额外硬拦截——tool_call 是 submit_image_to_video 但 source_image_url 为空时，强制 should_block_tool=True。
  • route_after_reflection：要求 tool_call.tool_name == submit_image_to_video 且 params.prompt 非空 且 params.source_image_url 非空，才走 tool 分支。

如果图生提交被拦截，按顺序检查这三层。

8. 建议的测试用例

每次改 prompt 或节点逻辑后，建议固定跑这些用例。

闲聊

预期：

route = chat
不进入 creative_worker / i2v_worker
不调用 tool

泛创意

我想做一个小狗视频

预期：

route = creative
给 2-3 个方向
不设置 tool_call

选择方案

第一个不错

预期：

生成完整 prompt
awaiting_confirmation = true
不调用 tool

修改 prompt

改成更搞笑一点

预期：

prompt 被改写
reply 明确说明已修改
不调用 tool

确认生成（文生）

确认生成

预期：

creative_worker 返回 tool_call = submit_text_to_video
reflection_worker 通过
进入 tool_executor

图生

用这张图 https://xxx.png 做个视频

预期：

route = i2v（走 Python 快捷路径）

i2v_worker 设置 source_image_url
tool_call = submit_image_to_video（确认后）

未确认时问状态

提交了吗？

预期：

不调用 tool
回复当前还没有提交

9. 推荐看 trace 的顺序

一条 trace 最有效的阅读顺序：

1. video_creation_agent 总输入输出
2. memory_retriever / retrieval_router 看记忆和检索
3. intent_router 看 route 是否正确
4. creative_worker / i2v_worker 看 prompt/reply/tool_call
5. reflection_worker 看是否拦截
6. route_after_reflection 看分支走向
7. tool_executor 看接口入参和响应
8. memory_writer 看记忆写入

不要一上来就看最底层 ChatOpenAI。先看业务节点 Output，通常更快。

10. 一句话经验

LangSmith 不是只看"模型说了什么"，而是看：

状态是怎么变的，
节点是怎么走的，
工具为什么调用或没调用。

对你这个 Agent 来说，最重要的字段是：

route
params.prompt
params.source_image_url（图生）
tool_call.tool_name
reflection_passed

只要这些字段符合预期，大部分流程就是正常的。
