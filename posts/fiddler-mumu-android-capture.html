Fiddler + MuMu 模拟器抓取 Android 应用接口实战

测试工具2026年5月6日

移动端接口测试经常会遇到一个问题：产品页面已经跑通了，但接口文档不完整，或者自动化脚本需要复现 App 的真实请求链路。这时，抓包就成了测试同学还原接口、理解业务流程、定位异常请求的重要手段。

这篇文章整理一套基于 Fiddler Classic 和 MuMu 模拟器 的 Android 应用抓包流程。目标不是单纯“能看到请求”，而是沉淀一套可复用的操作方法：环境怎么配、证书怎么装、代理怎么走、抓到请求后怎么分析，以及遇到 HTTPS 抓不到、请求为空、App 无法联网时该怎么排查。

抓包不是为了“偷看接口”，而是为了把移动端真实行为还原成可分析、可复现、可自动化的接口链路。

一、适用场景

Fiddler + 模拟器的组合非常适合测试工程师在非 Root 真机成本较高、接口资料不完整、需要快速还原请求链路的场景下使用。

  • 移动端接口测试前，先还原 App 真实请求参数。
  • 接口文档不完整时，通过抓包补齐 URL、Headers、Body 和响应结构。
  • 定位页面数据来源，确认某个功能对应哪个后端接口。
  • 编写自动化脚本前，先明确请求顺序、鉴权参数和关键字段。
  • 排查线上问题时，对比正常请求和异常请求的差异。
这套方法更适合内部测试、授权测试和自有应用分析。不要用于未授权 App、敏感数据采集或违反服务协议的场景。

二、整体原理

抓包链路可以理解为：让 MuMu 模拟器里的 Android App 不再直接访问目标服务，而是先把网络请求发给电脑上的 Fiddler，再由 Fiddler 转发到真实服务器。这样 Fiddler 就能记录请求和响应。

Android App → MuMu 模拟器代理配置 → Windows 本机 IP:8888 → Fiddler 代理服务 → 目标后端服务 响应返回： 目标后端服务 → Fiddler → MuMu 模拟器 → Android App

如果是 HTTPS 请求，还需要让模拟器信任 Fiddler 生成的根证书。否则 App 会认为中间代理不可信，请求可能失败，Fiddler 也无法解密 HTTPS 内容。

三、环境准备

  • 一台 Windows 电脑。
  • Fiddler Classic，建议使用 5.x 或以上版本，可从 Telerik Fiddler 官网 下载。
  • MuMu 模拟器，建议 Android 7.1 或以上版本。
  • 目标 Android App 安装包，也可以直接在模拟器应用市场安装。
  • 电脑和模拟器网络可互通，通常使用同一台机器运行即可。

如果后续需要抓 HTTPS 请求，建议提前确认测试场景是否允许安装代理证书，以及目标 App 是否存在证书绑定、代理检测等安全策略。

四、配置 Fiddler

4.1 开启 HTTPS 解密

打开 Fiddler Classic 后，进入：

Tools

             → Options → HTTPS

勾选 Decrypt HTTPS traffic。首次开启时，Fiddler 会提示安装并信任根证书，按提示选择信任即可。

如果测试环境中存在自签名证书或证书链不完整的服务，可以根据实际情况勾选 Ignore server certificate errors

。这个选项会降低证书校验强度，只建议在明确的测试环境中使用。

4.2 允许远程设备连接

进入：

Tools

             → Options → Connections

确认 Fiddler 监听端口为 8888，并勾选 Allow remote computers to connect。这个配置允许模拟器通过电脑 IP 访问 Fiddler 代理服务。

修改完成后建议重启 Fiddler，确保代理和 HTTPS 配置生效。

4.3 确认本机 IP

在 Windows 中查看当前电脑 IP，例如 192.168.0.X。后续模拟器代理需要填写这个 IP，端口填写 8888。

代理地址：192.168.0.X
代理端口：8888

五、配置 MuMu 模拟器

5.1 开启必要权限

在 MuMu 模拟器中，建议开启 Root 权限和可写系统配置。不同版本入口略有差异，一般在模拟器设置中可以找到相关选项。

开启后重启模拟器，确保系统配置生效。

5.2 设置 WLAN 代理

进入模拟器 Android 系统设置：



            设置 → WLAN → 当前网络 → 修改网络 → 高级选项 → 代理

将代理设置为手动：

  • 代理服务器主机名：填写 Windows 本机 IP，例如 192.168.0.X。
  • 代理服务器端口：填写 8888 。

保存后，可以先在模拟器浏览器中访问一个普通网页，确认网络仍然可用。如果网页打不开，优先检查 IP、端口、防火墙和 Fiddler 是否正在运行。

5.3 安装 Fiddler 证书

在模拟器浏览器中访问：

http://192.168.0.X:8888

如果代理配置正确，会看到 Fiddler 的证书下载页面。下载证书后，将证书命名为 fiddler.cer，并在 Android 系统中安装。



            设置 → 安全 → 从存储设备安装证书

安装完成后，重新打开目标 App，再观察 Fiddler 中是否出现 HTTPS 请求内容。

六、抓包实战流程

环境配置完成后，就可以开始抓取目标 App 的接口请求。

  1. 启动 Fiddler，确认左下角处于 Capturing 状态。
  2. 打开 MuMu 模拟器，启动目标 Android App。
  3. 按照测试路径操作 App，例如登录、进入列表页、点击详情、提交表单。
  4. 在 Fiddler 左侧会话列表中观察新增请求。
  5. 根据 Host、URL、请求时间和页面操作，标记关键接口。
  6. 打开请求详情，查看 Headers、Query、Body、响应状态码和响应内容。
  7. 必要时通过 File → Save → All Sessions 保存会话，方便后续复盘。

建议抓包时一次只操作一个功能点，不要连续点击太多页面。这样 Fiddler 会话列表更干净，更容易把页面动作和接口请求对应起来。

七、接口分析方法

拿到请求后，不要只盯着 URL。一个接口能否被还原，通常要看四类信息。

7.1 看请求入口

  • Host：判断请求属于哪个服务域名。
  • Path：判断接口模块和功能语义。
  • Method：区分 GET、POST、PUT 等请求类型。

7.2 看请求参数

  • Query 参数：常见于列表分页、搜索筛选、资源 ID。
  • Body 参数：常见于登录、提交、创建任务、复杂查询。
  • Headers：重点关注鉴权 Token、设备信息、版本号、渠道标识和内容类型。

7.3 看响应结构

  • 状态码：确认请求是成功、失败还是被网关拦截。
  • 业务码：很多接口即使 HTTP 200，也可能业务失败。
  • 响应 Body：确认页面字段和接口字段之间的映射关系。

7.4 看请求顺序

复杂业务通常不是一个接口完成的。比如进入详情页前，可能先请求配置、再请求详情、再请求推荐列表。自动化脚本要想稳定复现，就需要理解这些请求之间的先后关系和依赖字段。

八、常见问题排查

8.1 Fiddler 看不到请求

  • 确认 Fiddler 是否处于 Capturing 状态。
  • 确认模拟器代理 IP 是否填写为 Windows 本机 IP，而不是 127.0.0.1。
  • 确认端口是否为 8888，并且 Fiddler Connections 中允许远程连接。
  • 检查 Windows 防火墙是否拦截 Fiddler。

8.2 HTTP 能抓到，HTTPS 看不到内容

  • 确认 Fiddler 已开启 Decrypt HTTPS traffic。
  • 确认模拟器已安装并信任 Fiddler 证书。
  • 如果 App 使用证书绑定或网络安全配置限制，普通代理证书可能无法解密。

8.3 App 设置代理后无法联网

  • 先确认 Fiddler 正在运行。
  • 检查代理 IP 是否是电脑当前网卡 IP。
  • 关闭代理后 App 能联网，说明问题多半在代理、证书或防火墙配置。
  • 可以先用模拟器浏览器访问 http://192.168.0.X:8888 验证代理链路。

8.4 目标 App 有反抓包策略

部分 App 会检测代理、证书或调试环境。内部测试场景下，建议优先找研发确认是否可以提供测试包、关闭证书绑定、提供测试环境接口文档，而不是盲目绕过安全策略。

九、沉淀为测试资产

抓包的最终价值不只是“这次看到了接口”，而是把接口链路沉淀成可以复用的测试资产。

  • 整理接口清单：Host、Path、Method、Headers、Body、响应字段。
  • 沉淀关键业务链路：登录、列表、详情、提交、生成任务等。
  • 标注动态字段：Token、时间戳、设备 ID、签名、分页参数。
  • 补齐自动化脚本输入：请求顺序、依赖字段、断言字段。
  • 保留抓包会话文件，方便后续问题复盘。
页面操作 → Fiddler 抓包 → 还原接口请求 → 整理字段和依赖 → 编写接口自动化脚本 → 形成可回归的测试资产

总结

Fiddler + MuMu 模拟器的价值，不只是抓到一个请求，而是把移动端真实操作还原成可分析、可复现、可自动化的接口链路。

对于测试工程师来说，抓包能力是一项非常实用的底层技能。它能帮助我们在接口文档缺失、业务链路复杂、问题难以复现时，快速回到真实请求本身，找到页面行为和后端接口之间的关系。

但也要注意，抓包应只用于授权测试、内部排查和自有应用分析。涉及用户隐私、账号凭证、生产敏感数据时，需要严格遵守权限边界和数据安全要求。
