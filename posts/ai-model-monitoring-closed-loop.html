AI 模型任务监控与日志根因分析闭环实战

最佳实践2026年5月1日

AI 生成类任务的失败排查是个典型的痛点：你知道失败率升高了，但要搞清楚"为什么失败"，往往需要经历翻监控、查日志、问研发、复现问题这一系列繁琐的步骤。本文分享我们如何把"发现异常 → 定位样本 → 查询日志 → 根因分析"串成一个自动化闭环，让模型失败排查效率提升 10 倍。

一、痛点：失败告警只是开始，不是结束

模型生成类任务有一个典型问题：失败不是单点故障，可能来自参数、素材、模型服务、队列、三方依赖或网关超时。只看到"失败率升高"还不够，值班同学真正需要回答的是：

  • 哪个模型或类型在失败？
  • 最近失败是否连续出现？
  • 对应的 video_id 是什么？
  • 失败时后端日志里发生了什么？
  • 该优先找模型服务、任务调度、素材输入还是接口链路？
这套系统的目标不是只发一条告警，而是形成一条可追溯的完整链路。

二、整体架构：5 层闭环设计

定时拉取视频任务状态 → 识别异常模型和连续失败区间 → 提取关键 video_id → 推送钉钉告警 → 通过 aliyun-sls-query skill 查询 SLS 日志 → 交给 OpenClaw 解析日志并输出排查结论

2.1 数据采集层

通过视频任务查询接口拉取最近任务列表，核心字段包括：

  • video_id：后续查询日志的关键索引 ⭐
  • type：模型或生成类型，用于分组统计
  • status：任务状态，0=生成中、1=成功、2=失败
  • create_at：任务创建时间，用于判断最新失败区间
  • app_type、device_code：用于过滤非目标产品数据

设计重点：

  • 分页拉取，避免接口一次返回不完整
  • 先标准化字段，再进入统计逻辑
  • 过滤非目标产品数据，保证告警口径稳定
  • 按 video_id 去重，避免重复任务放大失败次数

2.2 异常识别层

监控逻辑不是简单统计失败数，而是优先关注"最新一段是否持续失败"。

目前核心判断有两类：

  1. 连续失败阈值：同一个 type 下，最新任务开始连续失败达到阈值（例如连续失败 10 次）
  2. 窗口无成功判断：最近窗口内失败数达到最低门槛，并且窗口中只有失败或生成中，没有成功记录
为什么这么设计？模型服务偶发失败很常见，单条失败不一定值得打扰；但"最新连续失败"更像正在发生的问题，优先级更高。

连续失败扫描算法伪代码：

def detect_continuous_failure(tasks, threshold=10):
    """检测连续失败"""
    consecutive_failures = 0
    failure_window = []
    
    for task in reversed(tasks):  # 从最新开始
        if task.status == 2:  # 失败
            consecutive_failures += 1
            failure_window.append(task)
        elif task.status == 0:  # 生成中，跳过但不中断
            continue
        else:  # 遇到成功，立即停止
            break
    
    if consecutive_failures >= threshold:
        return {
            "type": "continuous_failure",
            "count": consecutive_failures,
            "oldest_video_id": failure_window[-1].video_id,
            "newest_video_id": failure_window[0].video_id,
            "oldest_time": failure_window[-1].create_at,
            "newest_time": failure_window[0].create_at,
        }
    
    return None

2.3 告警通知层

告警通过钉钉机器人发送，但内容不只告诉"失败了"，而是直接给排查入口。

推荐告警结构：

🤖 自动化测试 · 失败监控告警 统计范围：最近 N 条任务 需关注模型：X 个 1. 模型名称（type=xx） 告警原因：最新连续失败达到阈值 统计结果：连续失败 xx 次 失败区间：oldest_time ~ newest_time video_id：oldest_video_id -> newest_video_id

这里的 video_id 是整个闭环里最关键的信息。它既能让业务同学定位失败样本，也能让后续日志查询有明确关键词。

2.4 调度运行层

使用单进程循环调度器常驻运行，负责按固定周期触发失败监控任务。

当前调度策略：

  • 失败监控任务：默认每 10 分钟执行一次
  • 日报任务：每天固定时间执行
  • 每个任务用 safe_run 包裹，避免单次异常导致进程退出
  • 每轮执行打印开始、结束、下一次执行时间，方便定位运行状态
调度层只做编排，不写业务判断。这样后续要替换为 crontab、Supervisor、systemd 或 CI 定时任务时，核心监控逻辑不用改。

2.5 日志分析层

当告警出现后，系统已经给出了异常模型和关键 video_id。接下来通过 aliyun-sls-query skill 让 AI 进入日志分析流程。

日志分析四步走：

  1. 以 video_id 作为关键词查询阿里云 SLS
  2. 拉取指定时间窗口内的命中日志
  3. 解析日志中的错误栈、请求参数、服务返回、耗时和上下游调用信息
  4. 汇总成排查结论

典型输出模板：

📋 初步判断：失败集中在模型服务调用阶段，日志中多次出现 timeout。 🔍 关键日志摘要： - POST /api/v1/generate → 504 Gateway Timeout - 平均耗时超过 120s，触发网关超时 - 同一时间段内多个 type 均出现类似问题 💡 建议动作： 先确认模型服务可用性和队列积压情况， 再检查该 type 的参数是否近期有变更。

这一步的价值在于把"告警"升级成"可操作的初步诊断"。值班同学不需要先手工打开 SLS、拼查询条件、筛日志，再猜可能原因。

三、关键设计思路

3.1 用 video_id 串联业务状态和系统日志

整个方案的关键不是监控脚本本身，而是找到一个稳定的关联键。选择 video_id，因为它同时出现在：

  • 视频任务接口返回结果
  • 业务告警内容
  • 后端服务日志
  • SLS 查询关键词

只要告警里带上 video_id，后续所有排查动作都可以围绕它展开。

3.2 先判断"是否正在失败"，再判断"失败了多少"

很多监控会直接看失败率，但对生成任务来说，失败率有两个问题：

  • 样本小的时候波动很大，容易误报
  • 历史失败会稀释或放大当前问题，影响实时判断

当前策略更关注最新任务序列，回答一个值班最关心的问题：这个模型现在是不是还在连续失败？

3.3 告警只发"需要行动"的信息

内部告警最怕两种情况：

  • 信息太少：只说失败，不知道怎么查
  • 信息太多：一堆原始日志，没人愿意看

因此告警只保留四类信息：

  1. 结论：哪个模型异常
  2. 依据：为什么触发告警
  3. 范围：失败发生在哪个时间段
  4. 入口：用于日志查询的 video_id
告警的终点不是消息本身，而是下一步排查动作。

四、后续可演进方向

4.1 告警自动附带 SLS 查询提示词

可以在钉钉告警末尾直接生成一段可复制的指令：

请使用 aliyun-sls-query 查询 video_id=12345 的 SLS 日志，
时间范围覆盖 2026-05-01 10:00:00 前后 30 分钟，
并分析模型失败原因、关键错误日志和建议处理动作。

4.2 引入告警冷却和升级策略

  • 同一 type 在冷却期内不重复告警，避免刷屏
  • 连续多个周期异常后升级优先级
  • 恢复成功后发送恢复通知
  • 失败持续时间过长时自动扩大 SLS 查询范围

4.3 建立失败原因分类

日志解析结果可以沉淀成标准分类：

  • 输入素材问题
  • 参数兼容问题
  • 模型服务异常
  • 队列积压或超时
  • 第三方依赖异常
  • 发布变更引入
  • 未知问题，需要人工确认

后续日报可以统计"失败原因分布"，帮助研发从救火转向治理。

五、风险与注意事项

  • 权限风险：SLS 查询涉及线上日志权限，使用范围要受控，避免把敏感日志扩散到不必要的上下文
  • 误报风险：连续失败阈值需要结合任务量调整，低流量模型阈值过高会漏报，高流量模型阈值过低会刷屏
  • 日志缺失风险：如果服务日志没有稳定打印 video_id，闭环会断在 SLS 查询阶段，需要推动业务日志规范化
  • AI 解析风险：AI 输出应定位为"初步诊断"，关键故障仍需研发结合代码、发布记录和监控指标确认

总结

这套方案的核心价值，不是多发一条告警，而是把"发现异常、定位样本、查询日志、形成初步判断"串成一个低成本闭环。

AI 时代的测试工程师，不应该只是发现问题的人，更应该是建设问题定位自动化能力的人。通过这套监控与分析闭环，我们把原来需要几小时的人工排查过程，压缩到了几分钟内完成，让整个团队都能从繁琐的日志检索中解放出来，把精力投入到更有价值的事情上。
