LangGraph Agent 测试笔记：视频创作图的状态与分支验收

这篇和 [SKILL_TESTING_BLOG.md](./SKILL_TESTING_BLOG.md) 是一套思路的两头：

  • Skill 那头：脚本能不能独立把 API、记忆、检索跑通；
  • 这篇：图上这一圈节点（路由、结构化输出、反思、工具、RAG、记忆）状态和分支对不对。

合在一起才敢说「端到端用得出去」。单测聊天回复好看，信息量不够。

---

一、本轮 Agent 完整流转（与代码对齐）

下面按真实编译图写，对应 video_agent/graph/builder.py 里的边和 video_agent/graph/routing.py 里的条件函数。CLI 每处理用户一行输入，就是一次 app.invoke：从 START 走到 END，全程读写同一个 CreativeState。

公共前缀（三条业务分支前都一样）

  • START → memory_retriever — 读本地 user_memory.json，注入 long_term_memory。
  • memory_retriever → retrieval_router — 结构化模型决定本轮是否需要 RAG；写入 should_retrieve、retrieval_query；清空上轮 rag_context。
  • retrieval_router → 条件边 route_after_retrieval — 有检索意图且有 query → rag_retriever；否则跳过到 intent_router。若进了 rag_retriever，下一跳固定到 intent_router。
  • intent_router — Python 快捷分支：含图片 URL + 图生关键词 → 直接设 route="i2v"；否则调路由模型，在 chat / creative / i2v 里选。
  • intent_router → 条件边 route_by_intent — 纯映射 route → 下一节点：chat→chat_responder，creative→creative_worker，i2v→asset_resolver。

分支 A：闲聊 chat

chat_responder → memory_writer → END

不经过 reflection_worker、tool_executor。

分支 B：文生 creative

creative_worker → reflection_worker → 条件边 route_after_reflection → memory_writer 或 tool_executor → memory_writer → END

分支 C：图生 i2v

asset_resolver → i2v_worker → reflection_worker →（与分支 B 相同的条件边）→ …

条件边一览

流程图

flowchart TD
  START([START]) --> MR[memory_retriever]
  MR --> RR[retrieval_router]
  RR -->|retrieve| RAG[rag_retriever]
  RR -->|skip| IR[intent_router]
  RAG --> IR
  IR -->|chat| CHAT[chat_responder]
  IR -->|creative| CW[creative_worker]
  IR -->|i2v| AR[asset_resolver]
  AR --> I2V[i2v_worker]
  CHAT --> MW[memory_writer]
  CW --> REF[reflection_worker]
  I2V --> REF
  REF -->|tool| TE[tool_executor]
  REF -->|end| MW
  TE --> MW
  MW --> END([END])

二、先分清两层：工具层 vs 图编排层

litmedia_client 里的 @tool 和底层 HTTP，最好能在不写 Agent 的情况下先验一遍。和 Skill 篇的主张一样：底座绿了再上编排，否则报错堆在一起很难拆。

图这一层只管：这轮用户话说完以后，CreativeState 里哪些字段变了、有没有走错边、该不该点工具。

四、各分支验收时盯什么

闲聊

  • route == chat，应出现 chat_responder，不进 creative_worker / i2v_worker。
  • 不调用 submit_* 工具。
  • memory_writer 仍会跑，但不应该把闲聊内容写进记忆（验证 should_write）。

文生（creative）

  • route == creative → creative_worker → reflection_worker。
  • 模糊一句话不应直接提交；明确确认后才应走到 tool_executor。
  • reflection_worker 若 should_block_tool，图上应拿不到 tool 分支。
  • tool_call.tool_name 应为 submit_text_to_video，不是旧的 submit_video_generation。

图生（i2v）

  • 有图 URL 且意图明确时应能进 asset_resolver、i2v_worker。
  • params.source_image_url 或 resolved_image_url 应对齐。
  • 缺图时不应还带 submit_image_to_video。
  • 如果 AI 误返回 submit_text_to_video，i2v_worker 内应自动纠正。

RAG

  • retrieval_router 决定要不要检索；不该每轮无脑查。
  • 若走了检索，retrieval_query 和召回 rag_sources 应对得上问题类型。
  • rag_service 是本地 Markdown 关键词匹配，不是向量检索；测试时要注意中文分词粒度。

长期记忆

  • memory_writer 的写入要有门槛（模型判断 + Python 置信度），避免把一次性废话写进去。
  • confirmed_prompt 类别只保留最近 5 条。
  • 旧版 5 个数组格式的 user_memory.json 能自动迁移。

五、完整测试方法

5.1 测试准备

  • 固定测试环境（Python 版本、依赖版本、模型配置）。
  • 准备好 ARK_API_KEY、LitMedia 相关密钥和 endpoint。
  • 打开 DEBUG 日志。
  • 若用 LangSmith，先确认项目名、API key、运行后能看到 trace。
  • 确认 langchain_openai 版本和 with_structured_output 的 method 参数一致。

5.2 覆盖范围（按风险维度）

  • 路径覆盖：闲聊、文生、图生、检索、记忆、提交/不提交。
  • 状态覆盖：route、params、awaiting_confirmation、tool_call 的关键组合。
  • 资源覆盖：有图/无图、资源合法/不合法、资源缺失后的降级。
  • 异常覆盖：结构化空返回、工具超时、接口报错、字段缺失。
  • 边界覆盖：长输入、模糊输入、多轮改写、连续确认/取消。
  • 观测覆盖：每个关键阶段都能在日志或 trace 里定位。

5.3 执行顺序（不要跳步）

  • 静态层：py_compile + import 验证。
  • 工具层冒烟：直接验证 submit_text_to_video / submit_image_to_video。
  • 图路径层：覆盖主要分支，只看路由和状态。
  • 提交层：确认 reflection → tool_executor 的放行与拦截。
  • RAG/记忆层：确认触发条件、输出结构和写入边界。
  • 异常恢复层：验证结构化空返回的重试/降级，确保进程不崩。

5.4 判定标准

  • 流程正确：节点路径和分支选择符合设计。
  • 状态正确：关键状态字段变化符合预期，不出现越权提交。
  • 结果正确：工具执行、检索、记忆写入与用户意图一致。

5.5 失败后的定位顺序

  • 先看 intent_router（路由是否错）。
  • 再看业务节点（creative_worker / i2v_worker 的结构化输出）。
  • 再看 reflection_worker（是不是被拦了）。
  • 最后看 tool_executor（入参是否拼错、接口是否失败）。
  • 如果是偶发错，看 structured_output_observation（首空/重试恢复/二次仍空）。

六、结构化输出：实际踩过的坑和预防

6.1 method 参数必须显式指定

langchain_openai 版本不同，with_structured_output() 默认 method 可能从 function_calling 变成 json_schema。如果底层模型不支持 json_schema，报 400。

当前代码显式写：

router_llm = llm.with_structured_output(RouteDecision, method="function_calling")
creative_llm = llm.with_structured_output(CreativeUnderstanding, method="function_calling")
reflection_llm = llm.with_structured_output(ReflectionResult, method="function_calling")
memory_llm = llm.with_structured_output(MemoryWriteDecision, method="function_calling")
retrieval_llm = llm.with_structured_output(RetrievalDecision, method="function_calling")

经验：不要依赖默认值。 不同环境安装的版本可能不同，这就是"公司能用家里不能用"的典型原因。

6.2 模型偶发空返回

处理方式（invoke_structured_with_recovery）：

  • 主路径：正常结构化调用。
  • 第一次拿到 None：追加 HumanMessage 重试一次。
  • 还不行：返回 None，节点用 ensure_creative_understanding 兜底 + generate_clarification_reply 动态生成追问。
  • 观测：DEBUG 日志里有 structured_output_observation，区分「首空」「重试恢复」「二次仍空」。

---

七、和 LangSmith / 终端相关的杂项

  • LangSmith：一棵树对应一轮 invoke；节点名对上 builder.py 里的 add_node。细节见 [LangSmith_测试经验.md](./LangSmith_测试经验.md)。
  • Windows 控制台：回复带 emoji 时 print 可能 UnicodeEncodeError，CLI 侧用 utf-8/errors=replace 兜底。
  • 工具名变更：旧版叫 submit_video_generation，当前代码是 submit_text_to_video / submit_image_to_video，以代码为准。
  • FrontendParams 新增字段：open_filter、sound_effect_switch、seed、is_feed 在工具调用时要合并到 payload，测试时确认没漏。

---

八、容易被忽略的边角

路由只靠模型也会飘 — 有「关键词 + URL」的快捷路径时，和纯模型路由要能互相印证；改 prompt 后以固定话术矩阵回归。 反思层与工具层的一致性 — reflection_worker 拦了工具后，reply/awaiting_confirmation 是否被清回合理状态，避免用户以为已经提交了。 I2V 与文生工具的混用 — 模型有时在图生路径吐 submit_text_to_video，i2v_worker 内会自动纠正，这一项要单独验。 RAG 与记忆的「有没有」 — 没检索不等于坏；写入记忆过少或过多都值得看 reason/should_write。 图生路径缺图的多层保护 — i2v_worker 压 tool → reflection_worker 硬拦截 → route_after_reflection 三重检查，确保缺图时不误提交。

---

九、发版前检查单

  • 工具层：submit_text_to_video / submit_image_to_video 最小可调用。
  • 图：py_compile/import 整个 video_agent 无语法错误。
  • 覆盖矩阵：确保 chat / creative / i2v / RAG / 记忆 / 异常都被覆盖。
  • 结构化：function_calling 路径可用；验证空返回的重试/降级不崩进程。
  • method 参数：所有 with_structured_output 都显式写了 method="function_calling"。
  • LangSmith（若启用）：项目名称、API key、run_name/metadata 是否方便筛查。
  • Windows：CLI 跑一次带特殊字符的回复无编码崩。
  • 记忆：闲聊不应写入长期记忆；confirmed_prompt 不超过 5 条。

---

十、小结

Skill 测的是脚本和接口；Agent 测的是状态和分支。 两篇文档叠在一起：底下命令行能闭环，上头状态机不超范围、不坏在空 JSON，再谈上线心里会踏实得多。
