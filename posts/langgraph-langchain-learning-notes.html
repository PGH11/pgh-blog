LangGraph 与 LangChain 学习笔记

这份文档结合当前目录里的 video_agent 包（根目录 image_agent.py 为兼容入口），解释 LangChain 和 LangGraph 分别做什么，以及一次用户对话是怎么被送进 AI、怎么更新状态、怎么最终调用接口的。

一句话理解

在这个脚本里：

  • LangChain 负责和大模型交互：创建模型客户端、组织消息、调用 AI、拿结构化输出。
  • LangGraph 负责流程编排：定义状态、节点、分支，让一轮对话按固定流程运行。
  • Pydantic 负责数据结构：约束 AI 必须返回什么字段，避免只返回一段不可控文本。
  • 普通 Python 负责业务逻辑：合并参数、生成签名、调用 LitMedia 接口。

可以理解成：

LangChain = 模型调用层
LangGraph = 状态机编排层
Pydantic = 数据协议层
Python = 业务执行层

当前脚本的整体流程

用户每输入一句话，脚本会跑一次 LangGraph：

User 输入
  ↓
memory_retriever → retrieval_router → [rag_retriever | skip]
  ↓
intent_router
  ↓
根据 route 分支
  ├─ chat      → chat_responder
  ├─ creative  → creative_worker
  └─ i2v       → asset_resolver → i2v_worker
  ↓
creative/i2v → reflection_worker
  ↓
根据 route_after_reflection 分支
  ├─ tool  → tool_executor
  └─ end   → memory_writer
  ↓
memory_writer → END

如果用户是在闲聊，比如：

你能帮我干嘛？

会走：

memory_retriever → retrieval_router → intent_router → chat_responder → memory_writer → END

如果用户是在创作视频，比如：

我想生成一个关于小狗的视频

会走：

memory_retriever → retrieval_router → intent_router → creative_worker → reflection_worker → memory_writer → END

当用户最终确认后，LangGraph 会继续进入工具节点：

... → creative_worker → reflection_worker → tool_executor → memory_writer → END

图生路径类似，只是把 creative_worker 换成 asset_resolver → i2v_worker。

1. LangChain 在脚本里的作用

1.1 创建模型客户端

脚本里通过 ChatOpenAI 创建模型：

llm = ChatOpenAI(
    api_key=ark_api_key,
    base_url=os.getenv(
        "ARK_BASE_URL",
        "https://ark.cn-beijing.volces.com/api/coding/v3",
    ),
    model=os.getenv("ARK_MODEL", "ark-code-latest"),
    temperature=0,
)

虽然类名叫 ChatOpenAI，但这里配置了 Ark 的 base_url，所以实际是通过 OpenAI 兼容协议调用 Ark 模型。

这里的关键参数：

  • api_key：模型调用密钥。
  • base_url：模型接口地址。
  • model：模型名称。
  • temperature=0：降低随机性，让结构化任务更稳定。

1.2 组织消息上下文

LangChain 使用消息对象和模型对话：

from langchain_core.messages import AIMessage, HumanMessage, SystemMessage

三类消息的作用：

  • SystemMessage：告诉模型角色、规则、输出格式。
  • HumanMessage：用户输入，或程序拼出来的当前上下文。
  • AIMessage：历史助手回复。

例如 creative_worker() 里会构造：

messages = [
    SystemMessage(content=CREATIVE_PROMPT),
    HumanMessage(
        content=(
            "当前内容参数：\n"
            f"{current_params.model_dump_json(...)}\n\n"
            "最近对话：\n"
            f"{history_to_text(...)}\n\n"
            f"是否正在等待最终确认：{state['awaiting_confirmation']}\n\n"
            "用户最新输入：\n"
            f"{state['user_input']}"
        )
    ),
]

这就是实际发给 AI 的上下文。

1.3 普通文本输出

chat_responder() 用普通 llm.invoke(messages)： 

response = llm.invoke(messages)

这种调用让 AI 自由返回一段文本，适合：

  • 闲聊
  • 能力介绍
  • 回答"你记得我刚刚说了什么吗"

返回后脚本用：

str(response.content)

拿到回复文本。

1.4 结构化输出

创作节点不是让 AI 随便返回文本，而是要求 AI 返回固定结构。

脚本里所有结构化输出都显式指定 method：

router_llm = llm.with_structured_output(RouteDecision, method="function_calling")
creative_llm = llm.with_structured_output(CreativeUnderstanding, method="function_calling")
reflection_llm = llm.with_structured_output(ReflectionResult, method="function_calling")
memory_llm = llm.with_structured_output(MemoryWriteDecision, method="function_calling")
retrieval_llm = llm.with_structured_output(RetrievalDecision, method="function_calling")

这里要特别注意 method 参数。

with_structured_output() 在 langchain_openai >= 0.2 里默认是： 

method="json_schema"

如果底层模型或 OpenAI 兼容服务不支持 response_format.type=json_schema，就会报类似错误：

InvalidParameter: response_format.type=json_schema is not supported by this model

当前脚本走的是 Ark OpenAI 兼容接口，所以显式写 method="function_calling" 更稳。 这样仍然由 LangChain 负责结构化输出和 Pydantic 校验，但不会依赖模型服务支持 json_schema 响应格式。

不同环境安装的 langchain-openai 版本可能不同，默认值可能从 function_calling 变成 json_schema。这就是为什么"公司能用家里不能用"——同样的代码和模型，只是包版本不同。

CreativeUnderstanding 是 Pydantic 模型： 

class CreativeUnderstanding(BaseModel):
    intent: Literal[
        "chat", "brainstorm", "create_prompt", "update_prompt",
        "update_negative_prompt", "confirm", "cancel",
    ]
    generation_mode: Literal["text_to_video", "image_to_video"]
    params_patch: CreativeParamsPatch
    merge_strategy: Literal["fill_missing", "overwrite"]
    reply: str
    needs_clarification: bool
    clarification_question: str | None
    ready_for_submit: bool
    confirm_submit: bool
    tool_call: ToolCallRequest

这表示 AI 必须返回类似这样的结构：

{
  "intent": "create_prompt",
  "generation_mode": "text_to_video",
  "params_patch": {
    "prompt": "短腿柯基在洒满午后阳光的客厅里追彩色毛绒球...",
    "negative_prompt": "画面昏暗、镜头剧烈晃动、场景杂乱"
  },
  "merge_strategy": "fill_missing",
  "reply": "我已经帮你整理成完整视频提示词啦。",
  "needs_clarification": false,
  "clarification_question": null,
  "ready_for_submit": true,
  "confirm_submit": false,
  "tool_call": {
    "tool_name": "none",
    "reason": "用户尚未明确确认"
  }
}

这样代码可以稳定读取：

understanding.params_patch.prompt
understanding.ready_for_submit
understanding.confirm_submit
understanding.tool_call.tool_name

这就是 with_structured_output 的价值：代码仍然拿到 Pydantic 对象，但底层结构化方式要和模型能力匹配。

1.5 结构化输出空返回的治理

模型偶发返回空结构化结果（运行时变成 None）。当前代码用 invoke_structured_with_recovery 处理：

raw_output = runnable.invoke(messages)
if raw_output is not None:
    return raw_output

# 第一次为空：追加一条要求重试
retry_messages = [*messages, HumanMessage(content="恢复要求：你上一条结构化输出为空。请严格按既定 schema 返回一个合法对象，不要返回 null。")]
retry_output = runnable.invoke(retry_messages)
if retry_output is not None:
    return retry_output

# 仍为空：返回 None，由节点降级处理
return None

节点拿到 None 后，用 ensure_creative_understanding 兜底，再调用 generate_clarification_reply 动态生成澄清回复。

观测上，可以在 DEBUG 或 LangSmith 里看到 structured_output_observation 日志，区分「首空」「重试恢复」「二次仍空」。

2. Pydantic 在脚本里的作用

Pydantic 用来定义"数据协议"。

2.1 Agent 内容参数

class CreativeParams(BaseModel):
    prompt: str | None = Field(default=None, description="最终视频提示词")
    negative_prompt: str | None = Field(default=None, description="负向提示词")
    source_image_url: str | None = Field(default=None, description="图生视频的参考图 URL")

这是 Agent 真正负责维护的内容。注意 source_image_url 是图生视频的参考图，属于内容参数而非 UI 参数。

2.2 前端 UI 参数

class FrontendParams(BaseModel):
    video_model: str = Field(default="54")
    video_num: int = Field(default=1, ge=1, le=4)
    ratio: str = Field(default="16:9")
    quality: str = Field(default="360p")
    duration: int = Field(default=5, ge=5, le=15)
    open_filter: int = Field(default=0, ge=0, le=1)
    sound_effect_switch: int = Field(default=1, ge=0, le=1)
    seed: str = Field(default="")
    is_feed: int = Field(default=0, ge=0, le=1)

CLI 没有前端页面，所以用 FrontendParams() 模拟前端已经选择好的值。

2.3 参数补丁

class CreativeParamsPatch(BaseModel):
    prompt: str | None = None
    negative_prompt: str | None = None
    source_image_url: str | None = None

每轮 AI 不直接改完整状态，而是返回一个"补丁"。

2.4 工具调用决策

class ToolCallRequest(BaseModel):
    tool_name: Literal["none", "submit_text_to_video", "submit_image_to_video"]
    reason: str = ""
    arguments: SubmitVideoGenerationInput | SubmitImageToVideoInput | None = None

旧版只有一个 submit_video_generation，现在拆成文生和图生两个。

3. LangGraph 在脚本里的作用

LangGraph 负责把多个节点组织成状态机。

3.1 状态定义

class CreativeState(TypedDict):
    user_input: str
    params: CreativeParams
    frontend_params: FrontendParams
    chat_history: list[ChatTurn]
    long_term_memory: str
    should_retrieve: bool
    retrieval_query: str
    rag_context: str
    rag_sources: list[str]
    resolved_image_url: str
    route: Literal["chat", "creative", "i2v"]
    reply: str
    is_ready: bool
    awaiting_confirmation: bool
    tool_call: ToolCallRequest
    reflection_passed: bool
    reflection_issues: list[str]

这就是每一轮图执行时传来传去的状态。

3.2 创建图

graph = StateGraph(CreativeState)

3.3 添加节点

graph.add_node("memory_retriever", memory_retriever)
graph.add_node("retrieval_router", retrieval_router)
graph.add_node("rag_retriever", rag_retriever)
graph.add_node("intent_router", intent_router)
graph.add_node("chat_responder", chat_responder)
graph.add_node("creative_worker", creative_worker)
graph.add_node("asset_resolver", asset_resolver)
graph.add_node("i2v_worker", i2v_worker)
graph.add_node("reflection_worker", reflection_worker)
graph.add_node("tool_executor", tool_executor)
graph.add_node("memory_writer", memory_writer)

3.4 添加边

graph.add_edge(START, "memory_retriever")
graph.add_edge("memory_retriever", "retrieval_router")

3.5 条件分支

当前图有三处条件边：

# 检索路由
graph.add_conditional_edges(
    "retrieval_router",
    route_after_retrieval,
    {
        "retrieve": "rag_retriever",
        "skip": "intent_router",
    },
)

# 意图路由
graph.add_conditional_edges(
    "intent_router",
    route_by_intent,
    {
        "chat": "chat_responder",
        "creative": "creative_worker",
        "i2v": "asset_resolver",
    },
)

# 反思后路由
graph.add_conditional_edges(
    "reflection_worker",
    route_after_reflection,
    {
        "tool": "tool_executor",
        "end": "memory_writer",
    },
)

3.6 结束节点

所有分支最终都汇入 memory_writer，再由 memory_writer 到 END：

graph.add_edge("chat_responder", "memory_writer")
graph.add_edge("tool_executor", "memory_writer")
graph.add_edge("memory_writer", END)

3.7 编译图

return graph.compile()

4. 核心节点

4.1 memory_retriever

职责：读取本地 user_memory.json，把长期记忆注入本轮上下文。

每个节点后续都能从 state["long_term_memory"] 读取。

4.2 retrieval_router

职责：用结构化模型判断本轮是否需要 RAG 检索。

写入 should_retrieve、retrieval_query；同时清空上轮的 rag_context。

4.3 rag_retriever

职责：当 should_retrieve=True 时，走本地 Markdown 关键词匹配检索。

把检索结果写入 rag_context 和 rag_sources。

4.4 intent_router

职责：判断这句话走聊天、创作还是图生。

有Python 快捷路径：用户输入含图片 URL 且命中「图生」类关键词时，直接设 route="i2v"，不调模型。

否则调 router_llm，在 chat / creative / i2v 里选一个。

4.5 chat_responder

职责：处理闲聊、能力介绍、上下文问答。

使用普通文本模型调用，不经过 reflection_worker。

4.6 creative_worker

职责：文生视频的创作核心节点。

调用 creative_llm 结构化输出，处理 params、reply、awaiting_confirmation、tool_call 等。

4.7 asset_resolver / i2v_worker

职责：图生视频路径。

  • asset_resolver：从用户输入等来源解析图片 URL。
  • i2v_worker：图生专用结构化节点（独立 prompt I2V_PROMPT），产出与 creative_worker 类似的状态字段。缺图时会压掉提交类 tool_call。

4.8 reflection_worker

职责：二次审查，可改 reply、清空或保留 tool_call。

图生路径有额外硬拦截：tool_call 是 submit_image_to_video 但 source_image_url 为空时，强制 should_block_tool=True。

4.9 tool_executor

职责：按 tool_call.tool_name 调文生或图生工具。

当前支持两种工具：

  • submit_text_to_video：文生视频
  • submit_image_to_video：图生视频

4.10 memory_writer

职责：每轮收尾，AI 决定是否写入长期记忆，再由 Python 合并、裁剪、落盘。

所有分支最终都会经过 memory_writer，包括闲聊和工具执行后。

5. 一次完整对话是怎么跑的

以这段为例：

User: 我想生成一个关于小狗的视频

第一步：CLI 写入状态

state = {
    **state,
    "user_input": user_input,
    "reply": "",
    "long_term_memory": "",
    "should_retrieve": False,
    "retrieval_query": "",
    "rag_context": "",
    "rag_sources": [],
    "resolved_image_url": "",
    "is_ready": False,
    "tool_call": ToolCallRequest(),
    "reflection_passed": True,
    "reflection_issues": [],
}

第二步：调用 LangGraph

state = app.invoke(state, config={...})

第三步：公共前缀

memory_retriever → retrieval_router → [rag_retriever | skip] → intent_router

第四步：进入 intent_router

AI 判断：

{
  "route": "creative",
  "reason": "用户表达了视频创作需求"
}

第五步：进入 creative_worker

AI 返回：

{
  "intent": "brainstorm",
  "generation_mode": "text_to_video",
  "params_patch": {},
  "reply": "我为你准备了3个不同风格的小狗视频创意方向...",
  "needs_clarification": true,
  "ready_for_submit": false,
  "confirm_submit": false,
  "tool_call": {"tool_name": "none"}
}

第六步：进入 reflection_worker

反思节点检查：

{
  "passed": true,
  "should_block_tool": false,
  "issues": []
}

第七步：route_after_reflection

tool_call.tool_name == "none"，走 "end" → memory_writer。

第八步：memory_writer

决定是否写入长期记忆，落盘，返回更新后的 long_term_memory。

第九步：CLI 打印回复并保存历史

print(f"Agent: {state['reply']}")
state["chat_history"].extend(...)

6. 最终确认与接口调用

当用户输入"确认生成"时，creative_worker 返回：

{
  "tool_call": {
    "tool_name": "submit_text_to_video",
    "reason": "用户明确确认提交"
  }
}

reflection_worker 再检查一次。如果通过，route_after_reflection() 返回 "tool"，图进入 tool_executor： 

# route_after_reflection 的判定逻辑
if state["tool_call"].tool_name == "submit_text_to_video" and state["params"].prompt:
    return "tool"
if state["tool_call"].tool_name == "submit_image_to_video" and state["params"].prompt and state["params"].source_image_url:
    return "tool"
return "end"

图生路径需要同时满足：tool_call.tool_name == submit_image_to_video、params.prompt 非空、params.source_image_url 非空。

7. Agent 参数与前端参数如何避免冲突

当前设计里：

Agent 负责 prompt / negative_prompt / source_image_url
前端负责 ratio / duration / model / quality / video_num / open_filter / sound_effect_switch / seed / is_feed

所以不会出现 Agent 说 9:16 而前端选 16:9 的冲突。

8. 调试输出怎么看

当前脚本默认开启调试输出：

DEBUG_AI_OUTPUT = os.getenv("DEBUG_AI_OUTPUT", "1") != "0"

开启后终端会看到：

[DEBUG] memory_retriever 长期记忆
[DEBUG] retrieval_router AI 判断
[DEBUG] intent_router AI 返回
[DEBUG] creative_worker AI 返回
[DEBUG] reflection_worker AI 返回
[DEBUG] structured_output_observation（结构化空返回时）
[DEBUG] memory_writer 写入长期记忆
[DEBUG] LitMedia payload

9. 当前代码里 AI 到底看到了什么上下文

9.1 retrieval_router() 给检索判断 AI 的上下文

包含：

  • RETRIEVAL_ROUTER_PROMPT
  • 当前内容参数
  • 长期记忆
  • 是否正在等待确认
  • 最近 6 条对话
  • 用户最新输入

9.2 intent_router() 给路由 AI 的上下文

包含：

  • ROUTER_PROMPT
  • 当前内容参数
  • 长期记忆
  • RAG 上下文（如有）
  • 是否正在等待确认
  • 最近 8 条对话
  • 用户最新输入

注意：走 Python 快捷路径时不调模型。

9.3 chat_responder() 给聊天 AI 的上下文

包含：

  • CHAT_PROMPT
  • 当前内容参数
  • 长期记忆
  • RAG 上下文（如有）
  • 最近 10 条原始对话
  • 用户最新输入

9.4 creative_worker() 给创作 AI 的上下文

包含：

  • CREATIVE_PROMPT
  • 当前内容参数
  • 长期记忆
  • RAG 上下文（如有）
  • 最近 10 条对话文本
  • 是否正在等待确认
  • 用户最新输入

9.5 i2v_worker() 给图生 AI 的上下文

包含：

  • I2V_PROMPT
  • 当前内容参数（含 source_image_url）
  • 最近对话
  • 是否正在等待确认
  • 用户最新输入

10. limit=6/8/10 是什么

这是代码里人为决定"给 AI 看最近多少条对话"。限制上下文长度是为了：

  • 降低 token 消耗。
  • 减少模型响应时间。
  • 避免旧信息干扰当前任务。
  • 防止超过模型上下文窗口。

当前脚本有长期记忆补充：memory_retriever + retrieval_router + rag_retriever。

所以 AI 依靠：

长期记忆 long_term_memory + RAG 上下文 rag_context + 最近若干条 chat_history

来理解上下文。

11. RouteDecision 的定义

当前代码里 RouteDecision 已经是显式类：

class RouteDecision(BaseModel):
    route: Literal["chat", "creative", "i2v"] = Field(
        description="用户意图：chat=闲聊, creative=文生视频, i2v=图生视频"
    )
    reason: str = Field(description="路由原因")

比旧版动态 type(...) 更易读、更易维护。

12. 如何给不同路由用不同模型

当前代码里所有节点都共用同一个基础模型。

如果想不同节点用不同模型，可以把 build_llm() 改成支持传模型名：

def build_llm(model: str | None = None) -> ChatOpenAI:
    return ChatOpenAI(
        api_key=ark_api_key,
        base_url=os.getenv("ARK_BASE_URL", "https://ark.cn-beijing.volces.com/api/coding/v3"),
        model=model or os.getenv("ARK_MODEL", "ark-code-latest"),
        temperature=0,
    )

对应关系可以是：

intent_router：快模型、便宜模型
chat_responder：普通对话模型
creative_worker / i2v_worker：创作能力更强的模型

13. 最终接口调用在 LangGraph 工具节点里

tool_executor() 内部按 tool_call.tool_name 调用对应工具：
  • submit_text_to_video：文生视频
  • submit_image_to_video：图生视频

参数来源：

state["params"]：Agent 生成的 prompt / negative_prompt / source_image_url
frontend_params：前端选择的模型、比例、时长、清晰度、数量等

两者合并成接口 payload。

14. 当前脚本的设计优点

职责清晰

Agent 只负责内容创作（prompt / negative_prompt / source_image_url），不负责 UI 参数。

可调试

结构化输出会打印出来，方便观察 AI 是否理解正确。

CLI 标准输出改成 UTF-8，避免 Windows 控制台编码问题。

可扩展

未来可以增加：

  • ui_params_suggestion
  • prompt 质量评分
  • 多语言翻译
  • 风格模板
  • 生成后轮询任务状态

状态可控

LangGraph 让每轮流程固定，不会让一个节点同时承担所有逻辑。

结构化输出有兜底

invoke_structured_with_recovery + ensure_creative_understanding + generate_clarification_reply 三层治理，避免模型空返回导致整个图崩掉。

图生路径有多层保护

i2v_worker 压 tool → reflection_worker 硬拦截 → route_after_reflection 三重检查，确保缺图时不误提交。

16. 状态流转专题：state = app.invoke(state) 到底做了什么

16.1 state 是什么

state 是 LangGraph 每轮执行时传来传去的状态字典，结构由 CreativeState 定义。

16.2 每轮用户输入后，先更新 state

state = {
    **state,
    "user_input": user_input,
    "reply": "",
    "long_term_memory": "",
    "should_retrieve": False,
    "retrieval_query": "",
    "rag_context": "",
    "rag_sources": [],
    "resolved_image_url": "",
    "is_ready": False,
    "tool_call": ToolCallRequest(),
    "reflection_passed": True,
    "reflection_issues": [],
}

注意：每轮开始会清空上一轮的中间状态（rag_context、rag_sources、resolved_image_url 等），避免沿用旧数据。但 params、chat_history、awaiting_confirmation 这些跨轮持久的状态不会清空。

16.3 app.invoke(state) 的执行过程

  • memory_retriever：读长期记忆。
  • retrieval_router：决定是否检索。
  • 可选 rag_retriever：执行检索。
  • intent_router：判断路由。
  • 根据路由进入业务节点（chat_responder / creative_worker / asset_resolver → i2v_worker）。
  • 创作路径进 reflection_worker。
  • 根据反思结果走 tool_executor 或直接到 memory_writer。
  • memory_writer：写入记忆。
  • END：返回最终状态。

16.4 route 是在哪里写入 state 的

写入位置在 intent_router() 的返回值里：

return {
    **state,
    "route": decision.route,
    "reply": "",
}

Python 快捷路径同理：

if has_image_url and has_i2v_intent:
    return {
        **state,
        "route": "i2v",
        "reply": "",
    }

16.5 条件边怎么用

三个条件边都只读 state 字段：

  • route_after_retrieval：读 should_retrieve + retrieval_query。
  • route_by_intent：读 state["route"]。
  • route_after_reflection：读 tool_call.tool_name + params.prompt + params.source_image_url。

16.6 为什么要写成 state = app.invoke(state)

LangGraph 不会自动修改外部变量，它返回一个新状态。不写 state = 就拿不到节点更新后的结果。

核心记法：

state 进去，state 出来。
